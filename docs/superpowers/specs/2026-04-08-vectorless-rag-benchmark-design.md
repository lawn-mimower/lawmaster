# Vectorless RAG Benchmark Design

**Date:** 2026-04-08
**Branch:** `benchmark/vectorless-rag` (new, off `main`)
**Goal:** Compare PageIndex (vectorless, tree-based retrieval) against the existing LightRAG (vector + knowledge graph) on the LawMaster legal corpus, measuring retrieval quality, answer quality, latency, and token usage using RAGAS evaluation metrics.

---

## 1. Decisions

| Decision | Choice |
|----------|--------|
| Approach | Side-by-side retrieval modules with shared benchmark harness |
| Vectorless framework | PageIndex (tree-based LLM navigation) |
| Evaluation scope | Retrieval accuracy + end-to-end answer quality + inference time + tokens |
| Test set | Auto-generated by Claude subagent (~28 questions) |
| LLM (benchmark runtime) | Kimi K2 0905 via Groq for both retrievers |
| LLM (evaluation judge) | Claude (subagent) via RAGAS |
| Documents | Factories Act 1948 + Capital Subsidy Rules |
| Metrics framework | RAGAS |

### 2.2 Retriever Interface

```python
from dataclasses import dataclass

@dataclass
class RetrievedChunk:
    text: str
    source_document: str        # e.g. "Factories Act, 1948"
    source_section: str         # e.g. "Section 2(m)"
    page_range: str             # e.g. "28-30"
    relevance_score: float | None

@dataclass
class AnswerResult:
    answer: str
    retrieved_chunks: list[RetrievedChunk]
    retrieval_latency_ms: float
    e2e_latency_ms: float
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int

class RetrieverBase:
    name: str                   # "lightrag" or "pageindex"

    def index(self, documents: list[dict]) -> None:
        """Build/load index from source documents."""
        ...

    def retrieve(self, query: str, top_k: int = 5) -> list[RetrievedChunk]:
        """Retrieve relevant chunks for a query."""
        ...

    def query_end_to_end(self, query: str) -> AnswerResult:
        """Full RAG pipeline: retrieve + synthesize answer."""
        ...
```

Both retrievers conform to this interface. The benchmark harness treats them identically.

## 3. Retriever Implementations

### 3.1 LightRAG Retriever

Wraps the existing `src/agent/rag.py` setup with the following changes for the benchmark:

- **LLM swapped to Kimi K2 via Groq** using LiteLLM (`groq/kimi-k2-0905`) instead of Gemini
- **Embeddings unchanged:** BGE-Large (BAAI/bge-large-en-v1.5, 1024-dim, local)
- **Query mode:** `mix` (vector + knowledge graph hybrid), `top_k=5`
- **Uses existing `rag_storage/`** — no re-indexing needed
- **Token tracking:** Intercept LLM calls to capture prompt/completion token counts from Groq API response

### 3.2 PageIndex Retriever

New integration using the `pageindex` library:

**Index building (one-time):**
- Input: source PDFs directly (`FactoryAct1948.pdf`, `capital_subsidy_Rules.pdf`)
- PageIndex parses each PDF into a hierarchical JSON tree
- Each node: `title`, `node_id`, `start_index`/`end_index` (page ranges), `summary`, child `nodes`
- LLM for index generation: Kimi K2 via Groq (through LiteLLM)
- Indices stored in `benchmark/pageindex_storage/<doc_name>/index.json`

**Retrieval (per query):**
1. Full tree index (compact, ~2-3K tokens of titles + summaries) loaded into LLM context
2. LLM reasons top-down: examines summaries → selects relevant branch → drills into children
3. LLM identifies target pages (e.g. pages 28-30)
4. Only those pages loaded into context
5. LLM reads actual content and synthesizes answer

**Chunk mapping for retrieval metrics:**
- PageIndex fuses retrieval and reasoning — no separate "retrieved chunks" list
- We capture the pages/sections the LLM navigates to as `RetrievedChunk` objects
- This allows fair comparison of retrieval precision/recall against LightRAG

**Configuration:**
- LLM: `groq/kimi-k2-0905` via LiteLLM
- `max_pages_per_node`: default (auto-determined by PageIndex)
- `max_tokens_per_node`: default

## 4. Test Set

### 4.1 Generation

A Claude Code subagent reads the extracted markdown documents:
- `extraction_output/FactoryAct1948_docling.md`
- `extraction_output/capital_subsidy_Rules_docling.md`

It generates ~28 questions across 6 query types:

| Query Type | Description | Count |
|---|---|---|
| Exact section lookup | "What does Section X say?" | 6 |
| Definition retrieval | "What is the definition of Y?" | 5 |
| Penalty/consequence | "What is the penalty for violating Z?" | 4 |
| Multi-hop reasoning | Requires connecting information across sections | 5 |
| Numerical/tabular | Specific numbers, limits, rates | 4 |
| Cross-document | Spans both Factories Act and Capital Subsidy Rules | 4 |

### 4.2 Test Set Format

```json
{
  "metadata": {
    "generated_by": "claude-subagent",
    "generated_at": "2026-04-08T...",
    "source_documents": ["FactoryAct1948_docling.md", "capital_subsidy_Rules_docling.md"],
    "total_questions": 28
  },
  "questions": [
    {
      "id": "q01",
      "question": "What is the definition of 'hazardous process' under the Factories Act?",
      "expected_answer": "Section 2(cb) defines 'hazardous process' as...",
      "source_section": "Section 2(cb)",
      "source_document": "Factories Act, 1948",
      "source_pages": "3-4",
      "query_type": "definition"
    }
  ]

```

### 4.3 Ground Truth

`source_section` and `source_pages` serve as retrieval ground truth. A retriever "hits" if its returned chunks overlap with the correct section/pages.

## 5. Metrics — RAGAS Framework

### 5.1 RAGAS Metrics

| Metric | Measures | Inputs |
|---|---|---|
| **Faithfulness** | Is the answer grounded in retrieved context? (no hallucination) | answer + retrieved chunks |
| **Answer Relevancy** | Does the answer address the question? | question + answer |
| **Context Precision** | Are relevant chunks ranked higher? | question + retrieved chunks + ground truth |
| **Context Recall** | Did retrieval find all needed chunks? | retrieved chunks + expected answer |
| **Answer Correctness** | Factual correctness vs ground truth | answer + expected answer |

### 5.2 Custom Metrics

| Metric | Measures |
|---|---|
| **Retrieval Latency (ms)** | Time for retrieval step only (`time.perf_counter()`) |
| **E2E Latency (ms)** | Full pipeline: retrieve + synthesize |
| **Prompt Tokens** | Input tokens (from Groq API response) |
| **Completion Tokens** | Output tokens (from Groq API response) |
| **Total Tokens** | Sum per query and aggregate |

### 5.3 Evaluation Judge

- **Library:** `ragas` Python package
- **Judge LLM:** Claude (via subagent or Anthropic API) — independent from the model being benchmarked
- **Evaluation runs post-benchmark** — does not affect latency measurements
- All RAGAS scores are 0.0–1.0

### 5.4 Aggregation

All metrics are aggregated:
- **Per retriever** — overall averages
- **Per query type** — breakdown across the 6 categories
- **Per document** — Factories Act vs Capital Subsidy Rules performance

## 6. Benchmark Harness

### 6.1 `run_benchmark.py` Flow

```
1. Load testset.json
2. Initialize both retrievers (load indices)
3. For each question:
   a. Run LightRAG retriever → RetrievedChunks + AnswerResult
   b. Run PageIndex retriever → RetrievedChunks + AnswerResult
   c. Record latency and token usage per call
4. Save raw results to results/raw_results.json
5. Run RAGAS evaluation (Claude-as-judge) on all results
6. Compute aggregated metrics
7. Save results/summary.json and results/comparison_report.md
```

### 6.2 Token Tracking

Both retrievers use Groq API. Token counts are extracted from the API response metadata:
```python
response.usage.prompt_tokens
response.usage.completion_tokens
response.usage.total_tokens
```

For PageIndex (which may make multiple LLM calls per query for tree navigation), tokens are summed across all calls in that query.

### 6.3 Latency Measurement

The harness calls `query_end_to_end()` once per question. Retrieval latency is measured internally within each retriever and returned in `AnswerResult.retrieval_latency_ms`. E2E latency is measured by the harness around the full call:

```python
t0 = time.perf_counter()
result = retriever.query_end_to_end(query)
result.e2e_latency_ms = (time.perf_counter() - t0) * 1000
# result.retrieval_latency_ms is set internally by the retriever
```

- New branch: `benchmark/vectorless-rag` off `main`
- All benchmark code lives in `benchmark/` — no changes to existing `src/` code

## 10. Out of Scope

- Modifying the existing LightRAG pipeline or agent
- Adding BM25/SPLADE/ColBERT (future work if benchmark shows gaps)
- Production deployment of PageIndex
- UI integration of benchmark results
- Re-indexing documents into LightRAG
