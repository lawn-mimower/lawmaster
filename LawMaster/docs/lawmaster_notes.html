§ 02

Amendments: node vs property

structural trade-off
graph centrality · traversal

For an amendment, what structure would be an appropriate balance?

→ amendment = new node
Too many amendments → too many nodes, with perhaps low centrality to each — useless for graph traversal.
→ amendment = node property
What if 5 laws : 10–20 amendments (upper case), how can amendments be accommodated in such a fashion effectively? Node properties would be bloated JSONs, and the graph indexing we do applies only to the main laws. Nuanced amendments sit as unsearchable, untraversable node properties.

In that case, indexing just dumps them in-context to an LLM and we PRAY that what comes out as a response is a well-considered, well-measured response.

NOT RELIABLE !!!

Conclusion Hence, meaningfully versioning in a temporal fashion seems like a good way to go.

§ 05

Pipeline Ⓐ — chunk enrichment

indexing pipeline
struct → NL → chunk → branch
FIG. Ⓐ
01 — struct path
Structural metadata translated into natural language, appended to chunk text.
02 — vector path
Appended chunk feeds the LLM for in-context metadata extraction, lands in Vector Store.
03 — graph path
Appended chunk also feeds ER-Extraction, which produces LightRAG nodes.
04 — persistence
LightRAG nodes are materialised into the KG Store.

Here, appending NL metadata to the chunk may provide the LLM with holistic understanding — to better extract in-context metadata — OR be entirely redundant and a waste of tokens and context window.

Really depends on the overlap between each metadata key. [How independent?]

§ 06

Big question: querying

retrieval layer
LightRAG vs Postgres

That is all well and dandy on the indexing side, but we ought to keep in mind that the indexing is for querying. What sort of multi-query, metadata-filtering-enabled, or mini-graph builder / explorer are we really considering here? That decides what to add/subtract from the indexing pipeline.

★ BIG QUESTION FOR QUERYING ★

Tools? → Does LightRAG allow metadata filtering for queries?

For vector aspects, maybe sure. But KG metadata is really limited — can filters be applied here? Is the hassle worth it?

If LightRAG is restricting the kinds of indexing parameters we have discussed till now, AND also being restrictive on querying — what is the point?

OR
Alternative route Do we go the route of Postgres storage [via or via not LightRAG]?
  • Blazing fast querying.
  • Realtime query generation.
  • All kinds of filters.
  • + vector store too.
